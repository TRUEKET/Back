# 대화 판독 서버 규칙

## 호출 경계

이 모듈은 POST /analyze에서 AI가 추출한 신호를 검증하고 대화·신고·최종 단계를 계산한다. AI는 근거를 추출하고 최종 단계는 서버 규칙이 결정한다. 신호 계산용 별도 공개 API는 추가하지 않는다.

`ChatStageService.assess(AnalysisInput)`에 거래 유형, 유형 불일치 여부, 문장 목록, AI 신호 후보를 전달한다. 기존 `TradeType`을 사용하고 유형을 알 수 없으면 OTHER로 처리한다.

문장은 서버의 OCR·대화 입력 처리 과정에서 문장 단위로 구분해 고유 id와 SELLER·BUYER·UNKNOWN 화자를 붙여야 한다. 신호 후보의 sentenceId는 그 id를 참조한다. 하나의 발화를 여러 문장으로 나눌 때도 서로 다른 id를 사용한다. 반복 캡처의 동일 말풍선은 입력 처리 단계에서 중복 제거해야 한다.

quote는 해당 판매자 문장에서 확인되어야 하고 reason은 비어 있으면 안 된다. 원문과 정확히 일치하면 그대로 사용한다. 일치하지 않을 때만 공백·줄바꿈과 허용한 문장부호 차이를 정규화해 연속 부분 문자열을 찾고, 실제 원문 구간을 복원해 근거로 사용한다. 구매자 발화, 화자 불명, 없는 문장, 지어낸 quote, 알 수 없는 신호 ID는 집계하지 않는다. 전처리 중 개인정보를 가리면 근거 검증용 문장과 quote에 같은 처리를 적용해야 한다.

## 신호 사전

`src/main/resources/analysis/signals.json`에서 버전·기준·세기·활성 여부·예시를 관리한다. 현재 버전은 사용자가 제공한 v0.2다. name·definition·notSignal·examples·counterExamples를 포함하며 활성 신호의 전체 JSON이 AI 프롬프트로 전달된다. AI는 세기를 정하지 않으며 서버는 신호 ID의 정의를 사용한다.

S-E3는 후보, S-F2는 삭제된 신호로 비활성화했다. S-C2는 v0.2에서도 활성이다. F2 비활성·D1 주의·신분증 선제 제시 중립 등 이번 파일의 명시적 정책을 그대로 유지한다. S-X는 항상 주의이고 기준 칩 6개에 포함하지 않는다.

일반적으로 한 문장에서 신호 하나를 선택한다. 강함을 우선하고 같은 세기에서는 A > B > C > E > D > F > X 순서다. 문서의 명시적 예외와 T01에 따라 유형 불일치가 있고 S-A1이 선택된 문장에서 S-F1이 함께 검출되면 두 신호를 유지한다. 같은 신호는 서로 다른 문장에서 최대 두 번 집계한다.

아옮·대리티켓팅·취켓 대행은 S-A1을 informationalSignals로만 반환한다. 집계와 A 기준 칩에는 반영하지 않고 accountNoticeRequired를 설정하며 결과 화면의 트루샷 버튼을 숨긴다. S-A2는 모든 거래 유형에서 강함이다.

## 단계와 화면 조건

- 강함 한 개 이상이면 DANGER
- 주의 세 개 이상, S-X를 제외한 신호 두 개 이상, 서로 다른 A~F 기준 두 개 이상이면 DANGER
- 나머지 유효 신호가 하나 이상이면 SUSPECT
- 유효 신호가 없으면 SAFE

criteria는 A~F의 신호 세기를 별도로 표현한다. 주의 조합이나 신고로 전체가 위험이 돼도 해당 칩은 주의 또는 안전으로 유지한다. 클라이언트는 A·B·C·D·E·F 순서로 표시한다.

`FinalStageService.combine(chat, lookup)`은 식별자별 피해 신고 한 명 이상을 DANGER, 의심 제보 두 명 이상을 SUSPECT로 계산한 뒤 가장 높은 단계를 사용한다. 다른 식별자의 인원을 더하지 않는다. 대화와 신고 중 높은 것이 finalStage이고 동률인 유효 신고가 있으면 explanationSource는 REPORTS다.

ReportLookup.Target 인원은 서버 집계 결과다. AnalysisReportLookup은 신고 공통 정규화·HMAC과 유형으로 전체 식별자를 정확 매칭한다. PublicReportCounts는 최근 1년 created_at, 서로 다른 reporter_hash, PUBLISHED·RESPONDING·REVIEWING 상태, hidden 제외 조건을 적용한다 (#37). 형식 불명확 시 available=false 경고를 반환하면서 확인된 집계는 보존한다. FinalStageService 자체는 DB를 조회하지 않는다.

조회 실패는 available=false·targets 빈 목록으로 전달한다. 이 경우 대화 단계와 실패 안내를 반환한다. 조회 성공·이력 없음은 available=true·빈 목록이다.

showSuspicionReport는 대화 근거가 있을 때만 true다. 최종 안전이면 showReportButton은 false다. 신고로 위험이면 허용된 트루샷은 보조 버튼으로 내리도록 trueshotSecondary를 설정한다. 홈의 피해 신고 사실 확인 경로는 별도 흐름이다.

stageReportIdentifiers는 가장 높은 신고 단계에 해당하는 식별자 id 목록이고, raisedByReports는 신고가 대화보다 높을 때만 true다. 판독 결과는 복사된 불변 컬렉션으로 반환하며 이후 신고 변화로 자동 재계산하지 않는다.

## 검증

`bash gradlew test`

강함·주의 임계값, 계정 거래 예외, S-X 제한, 한 문장 중복·동일 신호 상한, 근거 원문과 화자 검증, 비활성 신호, 신고 단계 합산·동률·조회 실패·화면 조건을 검증한다. LLM 분류 정확도와 이미지 인식 품질 검증은 모델 연결 후 T01~T31 입력 대화로 별도 수행해야 한다.


## 인용문 검증 개선 (#80)

- 정확 일치가 우선이며, 실패한 경우 공백(탭·줄바꿈·전각 공백 포함), 마침표·쉼표·느낌표·물음표·물결표·말줄임표·일반 따옴표 차이만 허용한다.
- 숫자 사이 소수점·쉼표는 의미가 달라질 수 있어 보존한다. 1.5와 15, 서로 다른 계좌 숫자, 단어 변경·중간 생략·부정 표현 변경은 같은 인용으로 처리하지 않는다.
- 정규화 결과가 비어 있는 문장부호뿐인 인용은 거부한다. 편집 거리나 의미 유사도로 대체하지 않는다.
- 정규화 일치 시 화면·신고 근거에는 모델이 고친 문구 대신 실제 문장의 연속 구간을 반환한다. 기존 개인정보 가림을 그 뒤에 적용한다.
- sentenceId가 존재하고 SELLER여도 인용이 맞지 않으면 제외한다. 전체 원문으로 바꿔 자동 인정하지 않는다. BUYER·UNKNOWN·없는 ID도 기존처럼 제외한다.
- 오른쪽=구매자·왼쪽=판매자는 구매자 캡처의 일반 배치를 설명하는 지침이다. 화면 근거가 다르면 이를 우선하며 전달·인용·시스템 문장을 판매자 발언으로 추정하지 않는다.
- 사전의 추가 메타데이터는 ignoreUnknown으로 허용하지만 알려진 criterion·strength의 잘못된 값은 역직렬화 단계에서 계속 거부한다.

기존 계산 기준(강함 1개 DANGER, 유효 주의 1개 SUSPECT, A1 유형 예외·문장별 우선순위·반복 상한)은 유지한다. SAFE 표시명·판단 보류 상태·UI 안내 위치는 이번 변경에 포함하지 않는다.

재검증할 때 서버를 재시작하고 같은 캡처를 POST /analyze로 새로 올린다. 응답의 assessment.chat.dictionaryVersion이 v0.2인지 확인한다. 기존 판독 ID나 캐시된 결과를 재사용하지 않는다. 의미가 전혀 달라도 허용하는 변경은 아니므로 새 캡처의 신호·인용문과 기대한 결과를 함께 비교한다. 자동 테스트는 사전 전달과 검증 정책을 확인하며 실제 캡처의 모델 인식률을 보장하지 않는다.
