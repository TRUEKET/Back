RP 신고 리스트·조회·등록·이의제기는 신고 담당자, TS 요청·촬영·공유는 트루샷 담당자 영역이다. 그 외 담당자가 구현할 부분은 판독에서 이 기능들을 호출하는 경계와 계정 탈퇴 시 함께 삭제하는 연결이다.

회원 탈퇴는 기존 DB의 트루샷 테이블을 사용하며 트루샷 테이블과 연결되는 JDBC 삭제 흐름을 사용한다. Storage 미설정 또는 파일 삭제 실패 시 503으로 중단한다. Storage 버킷 2개는 실제 Private 생성 확인 및 기본값 반영을 완료했다. 로컬 Storage 키 설정과 합성 사진 삭제·재삭제 실호출을 검증했다. 신고 해시 계약과 판독 조회 연결을 반영했다 (#37). 남은 작업은 신고 등록 모듈 병합 후 실환경 확인과 배포 환경 통합이다. Gemini와 OpenAI 모두 합성 사례와 HTTP 판독 흐름까지 실호출 확인했다.

신고 등록용 `AnalysisReportSourceService` 내부 전달 경계 구현 (#28): 활성 로그인·판독 세션 소유권·만료 검증 후 원문 식별자와 가려진 채택 근거를 반환한다. 신고 담당자의 실제 등록 API 연결은 남아 있다.

판독-로그인 전환 검증 (#30): 익명 판독 후 로그인·동일 계정 재로그인은 유지하고 다른 계정 로그인 성공 시 이전 판독 결과를 제거한다. 실제 인증 필터를 거치는 H2/MockMvc 연동 테스트로 검증한다.

#37은 feat/#36의 정규화·해시 클래스 두 개만 원본 그대로 재사용한다. 배포 초안(feat/#32)은 원래 작업 공간에 보존하며 본 작업에 포함하지 않는다.

## 신고 생명주기 연결 검증 (#41)

2026-11-14 origin/develop(b894d67) 확인 시 신고 담당 feat/#36은 미병합이며 열린 PR이 없다. 해당 브랜치 ReportCreationService.validateAnalysis는 JD 계약 보완 전 임시 ANALYSIS_NOT_AVAILABLE 차단 코드가 남아 있다. 따라서 신고 등록 HTTP 성공/거부, 임시 증빙 정리, 등록에서의 두 신고 조건 사용 검증은 담당자 갱신·병합 후 진행한다. 이 검증을 위해 해당 브랜치를 develop에 합치지 않았다.

현재 병합된 코드의 H2 연동 검증:

- 저장소에 신고 테스트 데이터를 추가하면 다음 판독에서 SAFE→DANGER로 상승하고 최초 판독의 신고 가능 조건은 바뀌지 않는다.
- 신고 PRIVATE 및 식별자 hidden 변경 후 새 판독에서 해당 신고가 집계에서 제외된다. 다시 공개하면 반영된다.
- 실제 로그인/CSRF/DELETE /me HTTP 흐름으로 신고자 탈퇴 시 신고가 삭제되고 다른 사용자의 다음 판독은 SAFE로 내려간다. 다른 사용자의 계정과 기존 판독 스냅샷은 유지된다.

신고 테스트 데이터는 기존 JPA 저장소로 생성했으며 등록 API를 호출한 것이 아니다. 모델 응답은 합성, DB는 H2, Storage 사진은 없는 사례다. 실제 Storage 삭제는 앞선 별도 검증 범위다. 팀 DB/외부 LLM/배포 설정/트루샷 AI·CV 변경은 없다.

#43: 로그아웃 API 성공 시 해당 세션의 판독 스냅샷을 만료 대기 없이 제거한다. 실제 인증 필터를 통과하는 H2 테스트로 정상/익명 로그아웃·타 브라우저 보존·CSRF 실패 시 보존을 검증한다. 배포 초안과 트루샷 AI/CV는 변경하지 않았다.
