# 트루샷 7일 보관 만료 정리 (#51)

요청 생성 시 저장하는 `purge_at`(생성+7일)을 기준으로 원본·가림 사진과 요청·사진 DB 행을 자동 정리한다. 기존 컬럼과 인덱스를 사용하므로 새 SQL 적용이나 API 변경은 없다.

## 처리 흐름

1. `TrueshotExpiryJob.purgeExpiredRequests`를 1분 간격으로 실행한다. 이전 실행 완료 후 1분을 기다리므로 실제 삭제 시각은 작업 시간에 따라 달라질 수 있다.
2. 실행 시작 시각 이하의 `purge_at`을 가진 요청 ID를 오름차순으로 100건씩 조회한다. 마지막 ID 이후를 조회하므로 앞 배치가 삭제돼도 다음 대상이 누락되지 않는다.
3. 각 요청을 별도 트랜잭션으로 잠그고 만료 여부를 다시 확인한다. 이후 해당 사진 행도 ID 순서로 잠근다.
4. 남아 있는 `original_storage_key`와 `masked_image`를 수집해 Supabase Storage에서 먼저 삭제한다.
5. 모든 파일 삭제가 성공한 경우에만 사진 행을 삭제하고 요청 행을 삭제한다. 사진에 저장한 손 인식 결과와 요청의 판정 결과도 함께 삭제된다.

인증 성공·실패·진행 단계와 관계없이 보관 만료를 적용한다. 회원 계정과 다른 요청 데이터는 삭제하지 않는다. 이미 즉시 삭제한 원본, 사진 없는 요청, 가림 실패로 가림 파일이 없는 요청도 처리할 수 있다.

## 실패·중복·동시 실행

- Storage가 일부 파일만 삭제하고 실패하면 DB 행과 파일 키를 모두 보존한다. 이미 없어진 파일도 재삭제가 성공하도록 기존 Storage 삭제 클라이언트를 재사용한다.
- DB 삭제가 실패하면 DB 트랜잭션을 롤백하므로 다음 실행에서 동일 키로 재시도할 수 있다. 외부 Storage 삭제 자체는 DB 롤백으로 복구되지 않는다.
- 실패한 요청 ID와 오류 종류만 기록하고 다음 요청을 계속 처리한다. 실패한 요청은 다음 주기에 다시 조회된다.
- 요청 단위 잠금으로 여러 정리 작업을 직렬화한다. 먼저 삭제된 요청을 다시 처리하면 아무 작업도 하지 않는다.
- 회원 탈퇴·최종 판정·공유 처리와 같은 요청 잠금을 사용한다. 탈퇴와 함께 실행되더라도 먼저 끝난 작업 이후의 DB 상태를 다시 확인한다.

## 검증

H2 DB와 로컬 HTTP Storage 서버로 다음을 검증한다. 실제 Supabase 파일이나 팀 데이터는 테스트에서 사용하지 않는다.

- 정확한 만료 경계 포함 및 아직 만료되지 않은 요청 보존
- 원본·가림 사진과 DB 행 삭제, 다른 사용자·다른 요청 보존
- 이미 삭제된 원본 및 사진 없는 요청 처리
- 일부 버킷 삭제 실패 시 DB·키 보존, 재시도 시 없는 파일 허용
- 100건 배치 경계에서 삭제 누락 방지, 한 요청 실패 후 계속 진행
- 동시 정리 및 회원 탈퇴와 양방향 동시 실행

실제 Supabase·PostgreSQL 환경에서의 운영 통합 검증은 별도로 수행해야 한다. 이번 작업에서는 실제 데이터 삭제나 배포를 실행하지 않았다. 변경된 백엔드가 실행되면 기존 Storage 환경변수 설정으로 정리 작업이 동작한다.
